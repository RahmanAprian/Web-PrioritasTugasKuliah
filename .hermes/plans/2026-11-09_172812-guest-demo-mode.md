# Plan: Guest/demo access for research testers

## Goal
Allow 30+ article-study testers to enter the app without registering, use realistic task/course screens, and keep every guest change out of MySQL and normal user accounts.

## Current context / assumptions
- Existing app: `D:\student-task-priority`, Laravel 13, Blade, PHP 8.5, MySQL database `student_task_priority`.
- Existing auth routes are `/login`, `/register`, `/logout`; application pages live under `auth` middleware.
- Persisted user data belongs to authenticated users through `User::courses()`, `User::tasks()`, and per-user `PrioritySetting`.
- User requests an optional “Masuk tanpa daftar” path that does not save demo activity to database. The safest interpretation is an isolated, session-backed demo workspace with synthetic sample data and a separate session guard/state; do not create shared guest users or temporary records in MySQL.
- Keep normal registration/login and their DB writes unchanged. Guest can inspect dashboard, courses, and tasks, and may add/edit/delete demo records only in that browser session. Demo state resets when session is cleared/expires. No need to collect tester names/email or create a usage log unless user requests it.
- `php artisan test` is the project test command; PHPUnit is configured with SQLite `:memory:`. MySQL schema was migrated earlier. Before implementation, recheck `php artisan route:list`, relevant views/controllers, and current test status because code may have changed since this plan.

## Architecture / proposed approach
Implement a dedicated `DemoWorkspace` service using Laravel session storage to initialize sample courses/tasks/settings and mutate that in-memory session state; never use Eloquent writes for demo access. Add guest-accessible routes under a distinct `/demo` namespace and middleware that identifies a demo session without authenticating a `User`. Controllers branch explicitly on the dedicated demo route/session and use the service; regular `/dashboard`, `/tasks`, `/courses` remain behind `auth`, so ownership/security behavior stays intact. Add a visible “Mode Uji — data tidak disimpan” banner and a “Keluar dari mode uji” action. Add login/register CTA “Masuk tanpa daftar” linking to `/demo`; do not silently mix demo data into real-user pages.

### 3. Implement session-backed workspace service (5 min)
Add `app/Services/DemoWorkspace.php`:

On course deletion, remove linked demo tasks only after confirmation in UI; server operation follows submitted delete.

- Keep sample fixture small (e.g. 3 courses, 5 tasks across High/Medium/Low plus one no-deadline task) and make it obvious as fictional test content.

## Risks, tradeoffs, and open questions
- Session-backed demo changes are temporary. Closing/expiring the session or clearing cookies loses demo entries; this is deliberate to meet the no-database requirement.
- Server session storage may use the configured database session driver. That can create/update the framework `sessions` record, though it does not write application domain data. If “tidak nyimpen didatabase” means absolutely no database writes including session rows, implementation must instead use a client-side signed/encrypted cookie session driver or a dedicated non-DB session store for demo requests. Confirm desired interpretation before implementing; recommended interpretation is no user/course/task/priority records in MySQL.
- Cookie/session storage is browser-local and can be cleared or constrained in size. Keep fixtures small; do not allow unrestricted long descriptions or large uploads.
- Concurrent testers get separate sessions, but same browser profile shares the same demo session. Recommend private/incognito sessions for parallel testers on one machine.
- Demo must remain visibly marked so participants do not confuse synthetic fixtures with their own stored records or mistake temporary data for research-submitted results.
- Account creation from demo does not migrate demo data. State this explicitly unless user asks for a secure transfer workflow.
- Possible open scope: whether demo testers should be allowed to create/edit/delete temporary tasks/courses, or only view a canned walkthrough. Current recommendation enables CRUD in session because it makes usability testing realistic while still meeting no-domain-DB-write requirement.
